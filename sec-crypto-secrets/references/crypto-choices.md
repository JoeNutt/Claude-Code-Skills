# Cryptographic Choices and Failure Modes

Specific parameters age. Treat the numbers here as a floor and check current guidance
(your platform's crypto library defaults, OWASP, or NIST) for anything long-lived.

## Password storage

**Argon2id** is the default choice. Tune so a single verification takes roughly 0.5–1 second
on production hardware, then check it under expected concurrent load — a cost that protects
you offline can also become your own denial of service at the login endpoint.

| Function | Notes |
|---|---|
| **Argon2id** | Memory-hard; resists GPU and ASIC attack. Preferred for new systems. |
| **scrypt** | Memory-hard; good where Argon2 is unavailable. |
| **bcrypt** | Acceptable and widely available. Note the ~72-byte input truncation — pre-hash longer inputs. |
| **PBKDF2** | Only where compliance requires it. Not memory-hard; needs a very high iteration count. |

Rules that matter more than the parameters:

- **Unique random salt per password**, generated by the CSPRNG. Never a global or derived salt.
- **Store the algorithm and parameters alongside the hash** so they can be changed later.
- **Upgrade transparently:** on a successful login, if the stored parameters are below current
  policy, re-hash with the new ones.
- **Verify in constant time** using the library's comparison function.
- **Never truncate or pre-transform** the password beyond a documented pre-hash.
- Enforce a **minimum length** (long passphrases beat composition rules), check against known
  breached-password lists, and don't impose a low maximum.
- **Never encrypt passwords** — encryption is reversible, which is exactly what you don't want.
  If you can recover a user's password, so can an attacker.

## Symmetric encryption

Use an AEAD mode; it gives confidentiality and integrity together.

- **AES-256-GCM** or **ChaCha20-Poly1305** (better on hardware without AES acceleration).
- **Never ECB** — it leaks structure; identical plaintext blocks produce identical ciphertext.
- **Never unauthenticated CBC.** Padding oracles are practical and well-tooled.
- **Nonce/IV: unique per encryption under the same key.** For GCM, a repeated nonce is
  catastrophic — it exposes plaintext relationships and allows forgery. Use a random 96-bit
  nonce, or a counter you can prove is unique across restarts, instances, and threads.
- Bind context with the AEAD's **associated data** — record id, version, tenant — so a valid
  ciphertext cannot be moved to another record.
- Include a **key/version identifier** with the ciphertext so keys can be rotated.

## Key hierarchy

Don't encrypt everything with one long-lived key.

```
Root/master key      held in a KMS or HSM; never leaves it; rarely rotated
  └─ Data-encryption keys   generated per tenant / record / file
       └─ Ciphertext        stored with the wrapped DEK and a key version
```

Rotating the root then re-wraps the DEKs — no bulk re-encryption of the data. Derive
purpose-specific subkeys with **HKDF** rather than reusing one key for two jobs; a key used
for both encryption and signing is a downgrade path.

## Rotation

Design it in from the start, because a system that cannot rotate will not be rotated.

1. Support **two valid keys at once** — the new one for writing, both for reading.
2. Tag every ciphertext, token, and signature with a key id.
3. Re-encrypt or re-issue in the background.
4. Retire the old key only once nothing references it.

Rotate on a schedule, on suspected exposure, and on staff departure. A secret that has been
committed to a repository is compromised — rotate it; removing the commit does not help,
because clones, forks, caches, and CI logs retain it.

## Randomness

| Purpose | Requirement |
|---|---|
| Session ids, tokens, reset links, API keys | CSPRNG, ≥128 bits of entropy |
| Salts | CSPRNG, ≥128 bits, unique per record |
| Nonces / IVs | CSPRNG or a provably unique counter |
| Key material | CSPRNG, or a proper KDF |
| Simulation, sampling, test data | Any PRNG is fine |

Use the platform's cryptographic generator by name. A general-purpose PRNG is predictable
from a handful of outputs, and one seeded from the clock, process id, or a user id is
guessable outright. When generating a token, take raw random bytes and encode them — never
build one from a hash of predictable values like a timestamp plus a user id.

## TLS

- **TLS 1.3**, or 1.2 with modern cipher suites. No SSLv3, TLS 1.0, or 1.1.
- **Verify certificates**: chain, hostname, and expiry. Never ship a disable-verification
  option — the "temporary" flag for a self-signed dev cert reliably reaches production.
- **Internal traffic too.** "It's on the private network" has not been a security boundary
  for a long time.
- **HSTS** for browser-facing services; redirect HTTP to HTTPS and never offer a plaintext
  fallback for authenticated traffic.
- Certificate **pinning** only where you control the client and can ship updates — a pinned
  cert you cannot rotate is an outage waiting to happen.
- Automate renewal. Most TLS incidents are expiries, not attacks.

## Failure modes seen repeatedly

| Failure | Consequence |
|---|---|
| Homemade cipher or "encryption" by XOR/base64 | No protection at all |
| MD5 or SHA-1 for signatures or integrity | Collisions are practical |
| Plain hash for passwords, salted or not | Whole database cracked at GPU speed |
| ECB mode | Structure visible in ciphertext |
| Unauthenticated CBC | Padding oracle; ciphertext tampering |
| Nonce reuse under one key | Plaintext recovery and forgery |
| Non-crypto RNG for tokens | Session and token prediction |
| `==` on tokens or MACs | Timing side channel |
| Key committed next to data | Encryption provides nothing |
| Verification disabled "temporarily" | Trivial machine-in-the-middle |
| No rotation path | A leak becomes permanent |
| Secrets in logs, URLs, or client code | Leak through infrastructure you don't control |
| Encrypted field, unencrypted backup or search index | Breach via the copy |

## What not to over-engineer

Cryptography is not a substitute for the ordinary controls, and reaching for it first is a
common way to feel secure while remaining exploitable:

- Don't encrypt what you can avoid storing.
- Don't build a bespoke scheme where TLS plus an access check is the real answer.
- Don't add a second layer of application encryption over full-disk or database encryption
  without a threat it actually addresses — name the attacker it stops.
- Client-side encryption where the client also holds the key protects nothing from that
  client's user.
